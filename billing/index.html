user.sgit.ai / billing

The user keeps the meter

A proposed design for user management, activity and billing on vaults, with one billing vault per user, two signed writers, and one light check at the server. It is the design in the article of the same name, 21 October 2026, set out here as the billing half of this site, with its status kept honest: nothing in it is built, the record formats are sketches, and the Stripe flow is untested.

A proposal. The pieces it builds on exist and are in use today: the meter, the append lanes, the versioning and the key register. The billing vault, the admin vault, the credits API and the upload server's check do not. Every open question is listed at the end, and the one about where this lives is on the comms page.

In short

  • Billing is usually a server problem. A database, a balance every action updates, and races.
  • This proposal does it on the client. Each user has a billing vault; their browser keeps the meter.
  • Two writers, two keys. The user signs activity; the admin signs the validation of credit.
  • Credit now, validated later. The user carries on straight away; the admin side catches up.
  • Stripe is reconciled from the admin's browser. Payments are read, matched and validated.
  • One server, one light check. The upload server asks: is the key valid, and is there credit?
  • The user's data travels with them. Across every site, because it lives in their vault.

The old problem

Every time billing has been built here, it has had the same shape. A server and a database. Every action a user takes updates something central, a balance, a usage count, and the moment two actions arrive at once there is a race on that balance. The usual way out is to append first and update later, write every event to a log and work out the balance from it, but then either every action goes through the thing that updates the balance, which becomes the bottleneck, or the update runs on a schedule, a cron job or a set of functions, which works, and is messy, and is one more thing to run, watch and pay for.

The idea

The insight that makes it work is a simple one. A user very rarely runs several clients at the same time. The race that hurts a central server, many writers on one balance, mostly does not exist for one person's own activity. And for the cases where it does, two tabs, or a laptop and a phone, the vault's version control already does the merging. So each user has a vault that tracks their own activity. Their browser collects what they do, at intervals, and appends it there. That is the newsroom's meter, use first then buy or top up, with the record kept in a vault rather than only in one browser, so it can be backed up, synced, checked and billed.

Two writers, two keys

One billing vault per user, which two parties can write to, and each signs only what it is responsible for.

  • The user writes activity. Their browser commits what they used, signed with the user's key. That record belongs to them: they can read it, keep it and take it elsewhere.
  • The admin validates credit. When the user comes back from paying, their browser adds the credit straight away, with a signed claim. Later, the admin side checks that claim against Stripe and commits a validation into the same vault, signed with the admin key. Anyone can verify it against the admin's public key, and nobody else, the user included, can write a validation that verifies.

A validation record could be as small as this. The field names are a sketch, not a format:

{
  "billing_vault": "the vault's id",
  "claims": [
    { "claim": "the user's claim commit", "stripe_event": "the event's id",
      "pence": 500, "status": "validated" }
  ],
  "validated_balance_pence": 4210,
  "covers_activity_to": "the last activity commit counted",
  "as_of": "2026-10-21T10:00:00Z",
  "valid_until": "2026-10-28T10:00:00Z",
  "signed_by": "the admin key's fingerprint",
  "signature": "over everything above"
}

The user can add credit their browser believes in, but cannot make it validated, and the admin cannot invent activity the user did not sign.

The admin vault, and Stripe

The other half is a central admin vault, which the admin controls. Usage data flows into it from the users' vaults, close to anonymised but tied to the user so it can be billed, and it is where payments are reconciled with Stripe, from the admin's browser. Stripe's own constraints, from its documentation read on 21 October 2026, shape how:

  • Webhooks need a server. Registered endpoints must be publicly accessible HTTPS URLs, signed with a shared secret, not a public key. That does not fit a design with no server to receive them.
  • So the admin side reads instead. Stripe's API lists events going back up to 30 days, so the admin's browser pulls recent payments when it runs, rather than waiting for a push.
  • The key that reads Stripe stays on the admin's machine. Only publishable keys are safe outside a backend; here the admin's browser plays the backend, with a restricted key that can only read.
  • A payment can say which vault it is for. A payment link carries a client_reference_id, returned with the completed payment. It should be the billing vault's id, never anything secret.

So the flow is: the user is sent to Stripe with a payment link tagged with their billing vault; Stripe sends them back to a page that gives them the credit, and their browser adds it straight away and appends a signed claim; later, the admin's browser lists recent payments, matches each claim to a payment, and commits a signed validation. Two-way sync between two vaults, with each side writing only its own records.

Credit now, validated later

The user should be able to use what they paid for straight away, so the credit goes into their browser the moment they come back from Stripe. The check comes afterwards, as a layer on top. The admin side does not need to be online when the user pays; it can catch up hours later, and when it does it adds a note to the user's vault, signed as the commercial authority: validated, or not accepted. Stripe's own guidance fits this order: fulfilment cannot rely on the checkout landing page, because customers are not guaranteed to visit it; the admin side reads Stripe directly, so a payment whose user never came back is still credited.

Who is this defending against?

The party that could cheat is the user, by gaming the client: adding credit they did not pay for, or leaving out activity. In the short term that is unlikely, and it is easy to detect: every claim has to match a payment in Stripe, every commit is signed, and a claim with no payment behind it shows up as not valid the next time the admin side runs. So the design does not try to make cheating impossible on the client. It makes it visible, and puts the hard check where a mistake would cost money: at the server.

A vault shared by two parties

There is a more general idea underneath. The billing vault is shared by an untrusted party, the user, and a trusted one, the admin. Once the vault exists, its first commit is pinned. From then on every later commit can be checked for consistency against it: that it descends from that first commit, and that it is signed by a key we know. That gives a two-way channel between the two parties, through the vault, where it is always known who did what. Billing is the first use; the same pattern fits any place where a user and a service need a shared record both can trust.

The one server left

Most of the network's sites already run with no server of their own. The one that remains is the sgit upload server, which stores vaults, and it is also where usage costs money, in storage and transfer. So that is where the check belongs, and it stays light:

  • Is the key valid? A PKI check, against the register.
  • Is there credit? A read of the user's latest signed validation record, verified against the admin's public key.

The upload server does not compute a balance or keep a database of its own. It reads a cached, signed value through a small credits API with its own simple definition. A cached value can be slightly out of date, so the record carries valid_until, and the upload server can also count what it serves, so the units that cost real money are measured where they happen, not reported by the client. Today the access key gates use of the upload server but does not meter it; vault creation, for example, is not tracked per user. That is the gap this design fills.

What the user gets

This is not only a billing design. Once a user is logged in, their data lives in their vault, and it travels with them across all of the network's sites: what they read, what they set, what they bought, their keys and their preferences. A logged-in user gets a better experience on every site, without each site keeping a copy of them on a server. How the account travels is workflow 9, and it is not decided.

Open questions

  1. Where does it live? user.sgit.ai and api.user.sgit.ai, or billing.sgit.ai and api.billing.sgit.ai, so others can use it easily. Answered for this site on 21 October 2026: it is user.sgit.ai (N1). Whether billing also gets a site of its own, for others to use, is still open.
  2. Should the upload server accept unvalidated credit? Where usage costs real money, it may want only validated credit, or a small amount on top.
  3. Who creates the first vault? Maybe the service creates a user's first vault for them, when they first log in. The design assumes it already exists; the account model's first-device flow makes it with the access key the user pasted.
  4. How does login work? A PKI handshake, as everything now does. The account model answers the first half: the passkey, the door, the master, the key pairs. The handshake with a site is the second.
  5. How anonymous is the usage? The admin vault needs enough to bill, and should get no more.
  6. How often does the browser sync? Often enough to bill, not so often it slows the user down. The activity vault's answer today is: when the reader presses the button.
  7. How are refunds and disputes written? Probably as signed validation records too, with their own status.

The versioned API sites

Whatever the API site is called, it would follow the rule the network's other API sites already use, written down on api.send.sgit.ai: every release is a complete, independent copy at its own versioned path, never edited after it is published, with a manifest of hashes. A site pins the version it uses, so a change to the API is a new version, not an edit to an old one. The same rule is asked of any site whose code holds a session for the user.

What this does not claim

  • Nothing here is built. Neither the billing vault, the admin vault, the credits API nor the upload server's check exists.
  • The record formats are sketches. The field names will change.
  • The Stripe flow is not tested. Its constraints are from Stripe's documentation, read on 21 October 2026.
  • Client-reported activity is not proof. The design says where it is trusted and where it is counted.
  • The pieces it builds on exist. The meter, the append lanes, the versioning and the key register are in use today.
