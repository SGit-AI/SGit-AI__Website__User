user.sgit.ai / the account

The account model: door, master, vaults

You are already signed in, somewhere else: to Apple on a Mac, to Google in Chrome, to Microsoft on Windows, and that is where your passkeys live. The site does not need you to sign in to it. It asks the passkey store you already use for 32 bytes, computes from them the address and the key of a small door vault, finds the master's key inside, and the master holds everything else. There is no account database because there is no account, only vaults the user can open.

One clarification that matters. “The Google passkey” is a passkey for this site, registered by this page under this site's name, which your store keeps and syncs. It is not the passkey you use to sign in to Google, and a website cannot get PRF bytes from that one. The site learns a credential id, a public key and, after your gesture, 32 bytes. Not your email, not your name, not which account syncs it.

The derivation

From the bytes to a door, as the newsroom's lab runs it with the relying party newsroom.sgit.ai, and as this site's lab runs it with user.sgit.ai. Only the constant differs.

  1. The PRF input is a fixed, public value: SHA-256("user.sgit.ai/door/v1"). An input is not a secret; only the authenticator can turn it into the 32 bytes.
  2. The door seed is HKDF-SHA256(ikm = PRF bytes, salt = SHA-256("user.sgit.ai"), info = "sgit/door/v1").
  3. The door's passphrase and vault id are two more HKDF outputs from the seed. The passphrase is the hex of 32 bytes, keeping all 256 bits. The vault id is 8 characters of [a-z0-9] drawn with rejection sampling, so no character is favoured. The id is the door's address.
  4. The door vault key is the sgit vault key made of those two, and from there sgit's own derivation gives the read and write keys exactly as the command line does: PBKDF2-HMAC-SHA256 at 600,000 iterations, once for each. That is the cost of the design: door, master and reading vault need up to six derivations, about 105 ms each in headless Chromium on a four-core machine, several times slower on a phone, so a cold unlock can spend two to four seconds deriving keys before it fetches anything.
  5. The recovery door is the same, with the recovery code in place of the PRF bytes: 26 characters of base32, 128 bits, made by the page and shown once.
  6. Collisions are not a practical worry with 368 possible ids, but the page checks: a derived address that already holds something it cannot open is skipped, with a counter in the HKDF info.

The browser and the command line agree byte for byte: the newsroom publishes test vectors computed with sgit's own Python, and this site's lab runs the same derivation through its own copy of the code and compares every value when the page opens.

Every record is the meter's own, unchanged, plus the device that originated it. A record has exactly one author for ever: the device, and a device is a bucket the reader names. The totals are recomputed every time they are shown:

A door per path

The unit of the design is the path, not the passkey, because of a test. The same Google Password Manager passkey gave the same bytes in Chrome on a Mac and in Safari on an iPhone through the provider on each device, and a different set of bytes, consistently, when an iPad or that same Mac reached the phone by QR code. Apple's forums report the same for iCloud Keychain since late 2024.

RunClientHow the passkey answeredBytes
1Chrome on a MacGoogle Password Manager on the Mac, Touch IDA
2Safari on an iPhoneGoogle Password Manager on the phone, Face IDA
3Safari on an iPadA QR code, scanned by the iPhone; the phone's provider answeredB
4Chrome on the same Mac, “use a phone, tablet or security key”A QR code, scanned by the same iPhoneB

So whatever produced a distinct set of bytes gets a distinct door, and every door points at the same master and says where it came from. If a provider's fix moves a path's bytes, that path finds no door, says so, and the reader adds one. The design never has to guess which output was correct. It only has to keep every door replaceable. That is also why the master's key is random and sits behind a door rather than being derived from the bytes directly: derived directly, a path with other bytes would derive another master, and nothing could join the two.

Security, said plainly

  • What each party sees. The vault server: ciphertext, sizes, times and ids that look random. Your platform account: that a passkey exists for this site, under the name you gave it. The provider that answers a PRF request: the request, and that it answered. Only this page, in your browser, after your gesture, holds the PRF bytes and the keys.
  • Whoever can use the passkey by a path that has a door can reach everything below the master. That is exactly the passkey's protection, the biometric, the device and the store, and nothing in this stack adds to it or weakens it. A second passkey for an admin master is how the reach is split.
  • A path's bytes are a key a provider lends. Two paths can compute different bytes from one credential, and a provider's fix could change either. The door layer makes that survivable: no door is the only way in.
  • The origin loads no third-party scripts, on any page. Storage is per origin. Enforced by the build.
  • The relying party ID is a trust boundary. This site registers passkeys for user.sgit.ai exactly.
  • Passkeys cannot be phished across sites. They are bound to the site's name; a look-alike domain gets nothing.
  • Losing everything is final. Every door's passkey and the recovery code gone means no one can open the vaults. That is the property that makes the design worth having, and the first run says so before it shows the code.
  • Availability is not secrecy. The vault server could delete or roll back ciphertext. It cannot read it. The local copy covers the first; nothing is needed for the second.
  • Agents do not have passkeys. An agent that should read part of a user's data gets a read key for one vault, given by the user from the master, never the master itself.
  • Activity reported by the browser is on trust where the cost to us is small. What costs real money, storage and transfer, is counted at the server where it happens.

When PRF is off, the page offers a ladder, in this order: sign in to a store, so the passkey syncs from now on; use your phone by QR, with its own door; plug in a hardware key; or stay on this device, where the browser's own copy keeps working and the recovery code is the way back.
