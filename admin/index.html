Admin and engineering

This site is hand-written static HTML with a few build tools and one gate. Nothing is compiled, there is no framework, and a human can open any page and edit it. What is not hand-maintained is the chrome and the version, because a site that will one day hold the door to a user's master vault should not drift, and one rule is enforced by the build rather than by intention: no script on this origin comes from anywhere else.

One definition of the chrome

admin/build/chrome.py holds the nav, the footer and the version badge, and rewrites them in place across every page in the tree. It also stamps the version into llms.txt, llms-full.txt and index.md.

The pre-release gate

admin/build/validate.js runs before anything is tagged or published, on pushes and on pull requests. A failure stops the release: no tag, no deploy. Five checks:

CheckWhat it catches
Version agreementAny page badge, the versions table, or either text twin disagreeing with version.txt.
Internal linksEvery relative link and source in every page must resolve to a file in the tree.
Canonical hostEvery page must declare where it canonically lives, and it must be on the host in CNAME.
Key-leak tripwireNothing in the tree may look like a vault key or an access key: the house shape, sgit's own sgit_private_vault_ shape, a 24-character or 64-hex passphrase joined by a colon to an 8-character id, or an access key prefix. Read keys are publishable and are not matched.
No third-party scriptNo <script src> or stylesheet from another origin on any page, and no import of another origin in any script. Browser storage is per origin, so a script on one page can read what another page kept; the passkey design names this as the one rule it depends on, and this gate makes it structural. The vault library, when it is vendored, will be served from here, pinned, never edited.

Beside the gate, admin/build/test_door.mjs checks the vendored derivation against the newsroom's test vectors, computed with sgit's own Python; it takes a second of PBKDF2 and is run by hand before a release. admin/build/check_siblings.py reports which sibling hosts answer, and is never a gate.

The pipeline

Every push to the release branch runs .github/workflows/deploy-pages.yml in three stages, the same pipeline as the sibling repositories (SGit-AI__Website, __Subscriptions, __PKI):

1

validate

The gate above. Runs on pull requests too, so branch work is checked before it can reach the release branch. A failure here means no tag and no publish.

2

tag-release

Every push to the release branch is a minor release, ending tagged. The version is owned by version.txt, bumped exactly once per release, and it must also appear in the release commit's subject as site vX.Y.Z:. CI verifies the two agree, that the bump is the next minor or a deliberate major, and then tags the release commit.

3

deploy

Publishes the tagged commit to GitHub Pages at the host in CNAME. Runs on manual dispatch even without a tag, and never when validation failed.

The release process

  1. Bump admin/build/version.txt once, and add a row to admin/versions.html. Update comms if the state of play changed.
  2. python3 admin/build/chrome.py, which propagates the version and any nav or footer change everywhere.
  3. python3 admin/build/gen_sitemap.py && python3 admin/build/gen_llms_full.py
  4. node admin/build/validate.js && node admin/build/test_door.mjs
  5. git commit -am "site vX.Y.Z: …" && git push to the release branch.

user.sgit.ai

The account is a vault, and the user holds it: a passkey opens a door, the door opens a master, the master holds the keys, and the user's browser keeps the record and the meter. No sign-in to the site, no account database, no server of ours that can read a thing. CC BY 4.0, part of the sgit.ai network.
