user.sgit.ai / the workflows

Ten client-side user workflows

User management on a site with no server of its own is not one feature. It is a set of things a person does, each of which their browser has to do entirely on its own, against a passkey store for the gesture and a vault server for ciphertext. These are the ten, as they run on newsroom.sgit.ai or as they are designed, on 21 Oct 2026. Each says what the user does, what the browser does, what leaves the browser, and where it stands.

The status chips. runs you can do it today, on the newsroom, as a beta with one reader. lab-proven a card in a lab did it once against a real vault server. designed written down in enough detail to build, not built. proposed an argument with its open questions listed. later named, with the ways it could go.
1

Sign in where you already are

What the user does. Presses one button and makes the gesture their device already asks for: Touch ID, Face ID, Windows Hello, a hardware key's PIN. No email, no password, no OAuth. The first screen is the passkey, and one line says that it lives in the store you already use and goes where it goes.

What the browser does. Asks the store for the passkey for this site with the PRF extension and a fixed public input. Gets 32 bytes. Derives the door's address and key from them (the derivation), fetches the door's one file, decrypts the master's key, opens the master, and from it opens the reader vault. Reading needs no access key, so a device that can open a door can read before it can write; the access key comes out of the master, so it can write too. The keys of an unlocked session are kept in memory and, for the life of the tab, in session storage, so moving from page to page does not ask for the passkey each time: a choice for the beta, written down so it can be revisited.

What leaves the browser. A PRF request to the passkey store. Plain GETs of ciphertext to the vault server. Not a name, not an email, not a password, not the bytes.

runs The vault pane on every newsroom page, since v0.11.0; the Vault button beside the balance. On this origin, the lab does the gesture and the derivation and stops before any server.
2

The first device: create the account

What the user does. Opens the pane, enables with the passkey, and is told no door here for this path yet. Pastes the access key, once, on this first device. Presses Create the account. Writes down the recovery code, shown once, after a sentence that says losing every passkey and the code is final.

What the browser does. Makes the master's key and the reader vault's key at random. Creates the door at its derived address, the master, the reader vault and the recovery door, with the access key. Puts the access key in the master, so a second device gets it by opening the master. Moves the reading account from this browser's local storage into the reader vault as the first device's file. From newsroom v0.12.1, an account made without an access key in its master asks for it once.

What leaves the browser. Encrypted commits, each one POST /batch to the vault server with the access key as a header, and a publish with compare-and-swap on the ref. The vault server stores ciphertext and hashes.

runs newsroom v0.11.0. The key pairs the brief asks for in the master (designed, step 5) are not made yet.
3

Open, or connect

What the user does. Chooses one of two ways in, and names nothing first. Open your vault with the passkey (or the recovery code, once): this browser reads and writes. Connect with a link from a browser where the vault is already open, as a URL, text or a QR code: this browser only sends, into the vault's inbox lane, and never reads, not even what it sent. The second is for a browser that cannot reach the passkey: a web view an app opened, a browser signed in to nothing, an old iPad kept light for reading.

Open your vaultConnect with a link

What the browser does. Four states: nothing; connected (the link in local storage, Send to my vault on every page); open with the device unknown; open with the device known. Opening is the full membership; connecting is the push-only one, and the site is not personalised there. What matters in that browser is that the reads, the decisions and the notes are captured, because they are the reader's own intelligence and the reason they come back.

What leaves the browser. Open: as workflow 1, plus commits. Connect: one account-less POST per send to an append lane, encrypted to the vault's public key, with a response that is deliberately blind.

runs newsroom v0.12.58, open, or connect; the inbox lane since v0.12.26.
4

Which device is this?

What the user does. After an explicit open, and only when there is a choice, answers one question: is this browser a device the vault already knows, or a new one? The chooser offers first the device whose name this browser used, or the one device on the same platform, and the button names the destination. Later, from the Vault tab, Change moves this browser into another device, and Merge ticks two or more devices and folds them into one with a name.

What the browser does. Choosing an existing device takes its id and label, and the merge that follows brings that device's records in as this browser's own. A new device needs no name. Two browsers may share a device, so every write is combine(prev, extract(local)) rather than an overwrite: every record of either, the one that knows more where both have it. A merge re-files each source into the target, keeps every record, removes the merged files from the current tree (every earlier version stays in the commits), and writes the merged ids to activity/aliases.json, so a browser still using one is filed under the merged device next time, and so is anything it sends. Nothing is dropped; a payment record is moved, never deleted.

What leaves the browser. Commits, as before. The device label is free text and only a hint; nothing is refused for a name.

runs The chooser in v0.12.58; merging, aliases and Change in v0.12.88, the vault, opened. Not built: splitting a merged device back out.
5

Update the vault, bring them here

What the user does. Reads. Presses Update the vault when they want this device's activity in the vault; the Vault button counts what is only in this browser, and a strip above the tabs offers the press on any page. On another device, presses Bring them here, or has it done for them: after an explicit open the merge runs on its own, because the reader asked for the vault and the vault is the account.

What the browser does. Local storage stays primary, written in real time by the meter; the vault is a copy the reader keeps current. One file per device, rewritten whole on every sync, one commit. Two devices never write the same file, so there is nothing to merge at the file level and no conflict by construction; the compare-and-swap on publish still guards the ref. The other direction, inbound(), counts what a merge would add without writing, and shows it as Not yet here. On a page change the saved session opens the vault silently and nothing is merged: a reload under a reader who is reading is not acceptable. A Calls tab names and decrypts every call the pane made to the vault server, so the reader can see what left and what came back.

What leaves the browser. One commit per press. Nothing on a timer.

runs newsroom v0.11.0, v0.12.6, v0.12.58, v0.12.88; the design in the activity vault. Not built: automatic sync on a timer or on leaving a page; pruning local records the vault already holds.
6

Read, and pay for what you read

What the user does. Reads. Starts with £5.00 of credit, is charged a few pence a page by how much of it they read, never less than a tenth of the page's price, and can go below zero without anything being blocked. Can pause all measuring, on every page, until they resume; reset a page to unread and have it refunded to the minimum; mark any section read or unread by hand; and say at the foot of a page that it was not worth it, in which case it is not charged. Tops up with a payment link when they want to.

What the browser does. Measures reading section by section: time on each section while the tab is in front and the reader active, against the section's words at 300 a minute, or text passing the reading line no faster than 450 words a minute. Keeps balance, history and receipts in local storage. Computes the totals from the records: reads, spent, declined, credit, balance = start + credit − spent. What was read also builds the reader's graph and their own front page.

What leaves the browser. Nothing, unless the reader chooses: a payment on Stripe's own page, a subscription, or a reading share. The reading itself is on trust: the reader can set the price of a page, edit their own balance, or start again in a private window. Every one of those changes a number only the cheater sees, so the gaps are accepted rather than closed with a server.

runs SG Meter v1.5.0 on every newsroom article, charging by what is read since v0.12.99 (17 October 2026); the controls in your reading, your controls.
7

Top up: credit now, validated later

What the user does. Follows a £5 payment link to Stripe's page, pays, and comes back. The credit is there the moment they return, and they carry on. Nothing central sits in the path of their work.

What the browser does, today. The return page gives the credit; the payment reference makes the top-up unique across devices, because a merged top-up is also added to the device's list of credited references, so a return page opened again on another device cannot credit the same payment twice.

What the browser does, as proposed. The payment link carries a client_reference_id, the billing vault's id, never anything secret. On return the browser adds the credit straight away and appends a signed claim, “I paid”, to the billing vault. Later, hours later if need be, the admin's browser lists recent payments from Stripe with a restricted, read-only key that stays on the admin's machine, matches each claim to a payment, and commits a signed validation into the same vault. Credit is then in one of three states, and the product carries on in all three because on the client it costs us nothing:

StateMeaning
Not yet validatedThe user paid, or says they did, and the admin side has not checked yet. Normal, and short-lived; a bank debit can take 2 to 14 days to confirm and simply stays here longer.
ValidatedThe admin side matched it to a payment in Stripe, and signed it.
Not validNo matching payment. Unlikely; it means an attack, or a bug, and it shows up the next time the admin side runs.

What leaves the browser. Today: the payment, on Stripe's page. Proposed: the signed claim, as a commit to the billing vault.

runs The payment link, live since 11 October 2026. proposed The claim, the validation and the three states: the user keeps the meter.
8

A new path, a lost device

What the user does. On a device whose path has no door (a new tablet whose only route is a QR code to the phone, or a path whose bytes a provider's fix has moved), reads no door here for this path yet, never an error, and takes one of two ways in: add the door from a device that is already open, or type the recovery code. In the first week, on a Mac with Chrome where both paths run, adds the QR path as a door in two gestures: open the door you have, then ask for the bytes by the other path. On losing a device, deletes its door from any open one.

What the browser does. Adding a door moves no key through a person: the page is unlocked, so the master's key is in memory; it derives the new door from the other path's bytes, encrypts the master's key under the new door's read key, writes the door's one file with the access key, and adds the door to the master's list. The provider that answered sees a PRF request and returns bytes; it never sees a key. A door is retired by deleting its one file, never by destroying its address, because the address is derived from the passkey and the path and would be lost for ever. Deleting a lost device's door stops that path from finding the master from the next unlock on; it does not undo a copy of the master's key the device may have had in memory, so the full answer is to rotate the master's key and rewrite the doors that are kept.

What leaves the browser. One door file, written. One door file, deleted.

lab-proven One door created at its derived address, opened again as a new device would, and deleted, on a real vault server; the pane's Add this device with the code runs. designed Adding a door by the other path while unlocked (the brief's step 6); rotating the master's key.
9

Across sites

What the user does, today. Nothing yet. The master is bound to the newsroom: its passkey is registered for newsroom.sgit.ai exactly, and a passkey for sgit.ai is ruled out, because any *.sgit.ai site could ask it for bytes and every one would have to be as strict as the strictest.

What is designed. The master already lists keys by site and purpose, and the billing article's promise rests on it: “because the user's data lives in their vault, it travels with them across our sites: what they read, what they set, what they bought, their keys and their preferences.” Two ways to get there are named, for later. A key hub, in the manner of secrets.sgit.ai, holds the master and hands a site only the key to its own vault, after the user approves it in a pop-up, the way a wallet connects to a site. Or WebAuthn Related Origin Requests let one passkey work on a list of related sites, in Chrome and Safari today.

The question this site carries. Is user.sgit.ai the hub, the origin that holds the door and hands each sibling the key to its own vault? Or does each site keep its own relying party and the hub stays at secrets.sgit.ai? Both are consistent with the two articles; neither has been decided. It is N3 on the comms page, put to the project lead rather than answered for tidiness.

later Named in The passkey opens the vault, part two, and in what the user gets.
10

Agents, messages and sessions

Give an agent a key. Agents do not have passkeys. An agent that should read part of a user's data gets a read key for one vault, given by the user from the master, never the master itself. An agent that should write gets its own private clone branch, and the work meets on a named branch a human reviews. runs as sgit's two-branch model; the handover from a master is designed.

Send a message. Every user now has a vault, every vault can have append lanes, and lanes plus PKI make a messenger: encrypted to the recipient's public key, signed by the sender, carried through a server that sees only ciphertext, size and time. The sender holds an append token that can write to one lane and nothing else; the owner holds the enum key that lists and fetches and cannot write. Messaging-FS is the proposed schema, one JSON file per conversation, next to Issues-FS and Email-FS. runs The reader vault's inbox lane (v0.12.26) and the newsroom's editor channel. proposed Deriving the lane address from the public key, one encoding, signing the whole envelope, the schema and the commands: Messaging-FS.

Hold a session. A temporary AWS session, one to twelve hours of credentials from the AWS access portal, pasted into a vault made for that session; the browser does the work with the normal AWS SDK for JavaScript, and what it finds, inventories, logs and costs, goes back into the vault, versioned and ready for graphs. The roles should be narrow, the sessions short, and the site's own code released the way the API sites are, each version a fixed, independent copy. proposed AWS from the vault; nothing built, and the name not decided.

What leaves the browser. A read key, handed to one agent for one vault. A sealed message, to a lane. AWS calls, from the browser, with credentials that live in the vault for the session and never in a page or a repository.

Three workflows that follow from the first nine: once the user holds the keys, every handover is a key given for one purpose, and every message is a signed file in a lane.

What they have in common

  • Nothing is typed twice, and no key passes through a person except the access key once and the recovery code where no door opens.
  • Every step runs in the browser, against the passkey store for the gesture and the vault server for ciphertext.
  • Records, never totals. Balance, reads and credit are recomputed from the records every time they are shown.
  • The user chooses when to sync. One button; nothing commits on its own.
  • Soft enforcement. The way in is never a form; a name is a hint; nothing is refused for a label. What the client reports is on trust where the cost is small, and counted at the server where the cost is real.
  • An unknown address is not an error. It means a door is not there yet, and the page says so.

The account is a vault, and the user holds it: a passkey opens a door, the door opens a master, the master holds the keys, and the user's browser keeps the record and the meter.
