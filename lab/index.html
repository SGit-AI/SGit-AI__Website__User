users.sgit.ai / the lab

The lab: passkey to door, on this origin

The first workflow, sign in where you already are, as far as it can go without a server: a passkey for users.sgit.ai with the PRF extension, the 32 bytes, the door's address and sgit's keys derived from them, a recovery code, and the newsroom's test vectors run through this site's own copy of the derivation. Every card says what it did in the log at the foot.

This page writes nothing to any server. It talks to your passkey store for the gesture and to nothing else: no vault is created, no door is looked for, no byte of yours leaves this page. The only lasting effect is a passkey in your store, named as you choose, which you can delete there. The code is assets/door.js, vendored from the newsroom's with the relying party made a parameter, and assets/lab.js. No script on this origin comes from anywhere else.

1 · This browser

What the page can know before it asks for anything. Whether PRF works cannot be known until a passkey is made: the store says then, and the page never guesses.

2 · Make a passkey for this site

A discoverable credential for users.sgit.ai exactly, user verification required, with the PRF extension asked for, under a user handle this page chooses at random and a display name for the role. Your store may offer a choice of where to keep it: iCloud Keychain, Google Password Manager, a phone by QR, a hardware key. Where it lives decides where the account goes.

3 · Get the bytes

One gesture. The page asks the store for the passkey for this site with the fixed public input SHA-256("users.sgit.ai/door/v1"), and the authenticator returns 32 bytes only it can compute. The card shows a fingerprint of them and the path the browser reports. The same passkey gives the same bytes on every device it syncs to, through the same kind of path; a phone over QR can give different bytes, and then the design gives that path a door of its own.

4 · Derive the door

HKDF from the bytes to a seed, a 256-bit passphrase and an 8-character address; then sgit's own PBKDF2 at 600,000 iterations, once for the read key and once for the write key, the cost the design pays on every cold unlock. The address is where this passkey's door would be. Nothing is fetched: the lab does not ask the vault server whether a door exists there.

5 · A recovery code

128 bits as 26 characters of base32, shown in groups of four to be written down, long enough to need no password stretching. It is the ikm of a second door, the one way in on a device where no door opens yet, and the one secret a person ever types.

6 · The test vectors, against sgit's Python

The newsroom publishes a fake PRF output and everything derived from it, computed in Python with sgit's own Vault__Crypto, for its relying party newsroom.sgit.ai. This site's copy of the derivation runs the same input with that relying party and compares seven values. It runs when the page opens.

Forget

Clears the bytes, the door and the keys from this page's memory and the remembered label from this browser. The passkey stays in your store; a site cannot delete a passkey, only you can.

The log

What this lab does not do

  • It makes no vault. The newsroom's lab goes further: with an access key kept in memory it makes real sgit vaults through the vault library vendored there, a door at its derived address, a master and a reader vault. This site has not vendored the library yet; that is T1 on the comms page, and when it is done the rule stays: pinned at a known commit, never edited, served from this origin.
  • It does not look for a door. A derived address with nothing at it would mean no door here for this path yet, never an error; the lab stops before the question.
  • It makes no key pairs. The identity the brief asks for, a signing pair and an encryption pair made at random and stored in the master, is designed and not built anywhere yet.
  • It is not tested by a virtual authenticator yet. The newsroom's pane is driven in Chromium with a virtual authenticator standing in for a synced passkey; this lab's derivation is checked by a Node test against the same vectors, and the gesture itself only by a person. T2.
  • It says nothing about which path is right. When two paths give different bytes, both need the credential's secret to check against the specification. The lab can say that each path was deterministic and that the two disagreed, and the design gives each a door.

users.sgit.ai

The account is a vault, and the user holds it: a passkey opens a door, the door opens a master, the master holds the keys, and the user's browser keeps the record and the meter. No sign-in to the site, no account database, no server of ours that can read a thing. CC BY 4.0, part of the sgit.ai network.
