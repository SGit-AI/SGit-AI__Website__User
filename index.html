An account with no server · ten client-side workflows · billing on the client · a lab

The account is a vault,
and the user holds it

No sign-in to the site, no account database, no server of ours that can read a thing. A passkey opens a door, the door opens a master, the master holds the keys. The user's browser keeps the record of what they did and the meter of what it cost, and both travel with them. This site collects the client-side user workflows of the sgit.ai network as they stand on 21 Oct 2026: what runs today on newsroom.sgit.ai, what is designed, what is proposed, and what is still open.

“Billing is usually a server problem: a server, a database, a balance every action has to update, race conditions, and either a bottleneck or a scheduler to keep it all in step. This is an exploration of doing it the other way round, on the client, with vaults.”

From The user keeps the meter, 21 October 2026, the article that proposes this site. The same move was made for the reading account a week earlier, in The passkey opens the vault: the account first, then the billing. This site is where the two meet.

Ten client-side user workflows

Each one says what the user does, what their browser does, what leaves the browser, and where it stands. Together they are the user management of a site with no server of its own.

1 · runs

Sign in where you already are

The passkey lives in the store you already use. One gesture gives 32 bytes; the bytes give a door; the door holds the master's key.

Read → 2 · runs

The first device: create the account

Paste the access key once. The door, the master, the reader vault and the recovery door are made; the code is shown once.

Read → 3 · runs

Open, or connect

Open the vault with the passkey and read and write; or connect with a link and only send, into an inbox lane.

Read → 4 · runs

Which device is this?

Asked once, after the open. Adopt a device the vault knows, or be a new one. Two browsers may share a device; devices can be merged.

Read → 5 · runs

Update the vault, bring them here

One file per device, rewritten whole, one commit. Both directions counted; totals recomputed from the records, never stored.

Read → 6 · runs

Read, and pay for what you read

£5 to start, a few pence a page by how much of it was read, pause and reset, and a balance that can go below zero.

Read → 7 · runs, then proposed

Top up: credit now, validated later

Pay on Stripe's page, come back, carry on. A signed claim now; a signed validation from the admin side later.

Read → 8 · designed

A new path, a lost device

“No door here yet” is not an error. Add a door from an open device or the recovery code; retire one by deleting its file.

Read → 9 · later

Across sites

The master already lists keys by site and purpose. A key hub, or related origins: two ways for one account to travel.

Read → 10 · mixed

Agents, messages and sessions

An agent gets a read key for one vault, never the master. Messages ride append lanes. An AWS session lives in a vault for an hour.

Four parties, each with its own key

The whole of user management, activity and billing comes down to four parties, and every one of them signs what it is responsible for and nothing else.

The user

Commits their own activity, and owns the record of it

Their browser meters what they do, appends it to their vault signed with their key, and adds credit the moment they pay.

Keys and parties → The admin vault

Writes the validations, collects the usage, reconciles Stripe

Can be offline for hours. Catches up from the admin's browser and commits a signed validation back into the user's vault.

Two writers, two keys → The upload server

The inline billing unit: is the key valid, is there credit?

The one server left, where usage costs real money. It computes no balance and keeps no database of its own.

The one server left → The credits API

A simple read of the signed credit

A cached, signed value with an end date, so the server's check stays small, and a cache a little stale is a known thing, not a bug.

The rules this origin keeps

A site that will one day hold the door to a user's master vault has to be as strict as the strictest page on it. These are the rules, and the first is enforced by the build rather than by intention.

1

No third-party script, on any page

Browser storage is per origin, so a script on one page can read what another page kept. Every script and stylesheet on user.sgit.ai is served from user.sgit.ai, and the pre-release gate fails the build on any other origin. The vault library, when it is vendored here, will be pinned at a known commit and never edited.

2

The relying party is this host, exactly

A passkey registered for sgit.ai would answer every *.sgit.ai site, and any of them could ask it for PRF bytes. The lab registers for user.sgit.ai and nothing wider. How one account travels across sites is a named question, not an accident of scope.

3

Read keys are printed; vault keys never are

A read key is derived one way and cannot be turned into write access, so it belongs in a page where a human can copy it. A vault key is write access and never touches a site. The gate greps the whole tree for key shapes.

4

Local storage stays primary; the vault is a copy the user keeps current

Nothing commits on its own. The number of commits is the number of times a person pressed the button. Automatic sync is a setting for later, once the cost of one is known.

5

Records, never totals

Reads, top-ups, claims and validations go in raw. Balance is recomputed from the records every time it is shown. A total copied from one device is wrong the moment a second device exists.
